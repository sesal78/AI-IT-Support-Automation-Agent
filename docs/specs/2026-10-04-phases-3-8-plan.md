|---|---|---|
| C1 | Staging (the live demo) builds from `main`; the e2e app builds from `dev` | Only Seun's `dev` → `main` merge releases code to the live demo, so the agent never self-releases (PROJECT §0) |
| C2 | The e2e app uses the separate Trigger.dev project (D10), deployed from `dev` by the agent; the main project's `prod` is deployed only at a release. `trigger.config.ts` takes the project ref from `TRIGGER_PROJECT_REF` (default: the main project) | Keeps the live demo's pipeline unchanged until Seun releases; gives e2e its own settings (2 min timeout, `E2E_MODE`) in the same cloud runtime; no secrets in a local process |

| C5 | Every ticket created by an app with `E2E_MODE=true` (form, email or `test-tickets`) is marked `is_test = true` by the server. Test switches (fault injection, cap and timeout overrides) are honoured only when the environment has `E2E_MODE=true` AND the ticket has `is_test = true` | Staging can never be switched by a payload; e2e data is always marked |

| C7 | The Slack reviewer allow-list (`SLACK_REVIEWER_IDS`) applies to every decision, not only auto-fix | Stricter than PROJECT §4 at no cost |
| C8 | The auto-fix target is always the ticket's caller (requester email → `sys_user`); ticket text never names the target | Stops "unlock someone else" requests |
| C9 | A target passes the auto-fix precheck only if ALL its roles are in an allowed set (default: `snc_internal` only), and the role read itself is proven to work | An allow-list fails closed; a deny-list of `admin` misses `user_admin`, `impersonator`, etc. |
| C10 | Requester email is NOT proof of identity (form or email). The Slack Approve is the identity control. Email-sourced tickets always go to review and are never eligible for auto-fix | Honest about the limit; recorded in PROJECT §12 |
| C11 | A dedicated Slack app is used for this project | A Slack app has one interactivity URL; the shared app may already use it |
| C12 | TypeSafe usage is metered by call count with `TYPESAFE_MONTHLY_CALL_CAP` (default 10 000, alert at 80 %) | TypeSafe pricing is not public; a count cap bounds cost |
| C13 | AI evals run through the real pipeline on the e2e environment (not in CI) | Spend is metered in one place; CI cannot reach the shared DB |
| C14 | Idempotency keys are namespaced by the server (`web:`, `email:`, `test:`) | A form request cannot claim an email's key |

## 2. Operating model for the autonomous loop

### 2.1 Standing approval (what the agent does alone)

The agent MAY, without asking:

1. Merge feature PRs into `dev` when CI is green and the adversarial review
   passed. Tasks tagged `high-risk` need two independent reviews (two fresh
   reviewer contexts) before the merge. Telegram gets a notification per
   merge. Seun can reply `stop` at any time; the loop halts at its next step.
2. Deploy `dev` to the e2e app and to the e2e Trigger.dev project (D10); roll
   either back or stop the e2e app.
3. After Seun merges a `dev` → `main` release PR: deploy `main` to
   `itsupport-web-staging` and Trigger.dev `prod`, and run the release smoke test.
4. Containment only: roll back staging or Trigger.dev `prod` to the previous
   version, then tell Seun at once (PROJECT §10 "contain first").
5. Create the Dokploy app `itsupport-web-e2e` (memory limit 512 MB) and switch
   staging's build branch from `dev` to `main` (one-time, P3-T0). It never
   writes secret values into either app.
6. Post, update and delete its own bot messages in `#itsupport-e2e`, and post
   alerts to `#ai-it-support-automation-agent`.
7. On ServiceNow `dev420188`: create, update and close incidents and work
   notes; set `locked_out` / `password_needs_reset` on seeded `demo.*` users
   for test setup and auto-fix tests. Nothing else on the instance.
8. Send test email from `e2e-sender@<project domain>` to the e2e intake address only.
9. Spend on TypeSafe and OpenCode Zen inside the caps (D5, C12).
10. Record a phase completion when every DoD item passes with evidence, update
    PROJECT §6/§11, and open the `dev` → `main` release PR.

Seun KEEPS (the loop pauses and asks):

- Merging every `dev` → `main` release PR (this is the release and the
  human review of all `high-risk` diffs: the release PR lists them with their
  test files, which Seun reads first)
- Applying migrations to the shared Supabase (D2)
- Every secret value, every env value in Dokploy / Trigger.dev, account creation
- Access and role changes: ServiceNow roles and users, Slack app install,
  Supabase Auth users, Cloudflare Access
- Pressing real Slack buttons on staging, including the one real auto-fix
  approval per release (§6.4 goal check)
- Any spend above a cap; destructive migrations; any new pending decision
- CI/CD changes not listed in §9

Limits the agent keeps regardless of approval: it never reads, prints or copies
a key-store value; never solves a CAPTCHA; never signs in with a real password
on a non-local host; never connects to the shared database; never holds the
service-role key or the real Slack signing secret in a test process.

### 2.2 The phase loop (one iteration = one phase)

1. **Preflight.** Re-read this plan, PROJECT §6/§11 and the phase section.
   Call `GET /api/health/config` on the e2e app: every feature the phase needs
   must be `configured: true`. Check the Dokploy host has ≥ 1 GB free memory.
2. **Human batch.** If a human step (§5) is missing, send ONE message
   (Telegram and chat) listing every missing step for the phase with exact
   names and paths. Re-check every 30 min. Never ask piecemeal.
3. **Spec.** Run `/spec` for the phase from the task list here. File tasks in
   ClickUp list `Build Loop`; hold dependent tasks as `blocked` with a HELD
   comment and release them in order (the build loop ignores dependencies).
4. **Build + review.** `/loop /build` and `/loop /review` run the tasks.
   Migrations are tested on `supabase/postgres:17.6.1.177` with phase-2-shaped
   seed rows, up → down → up; then the loop pauses once for Seun to apply them.
5. **Deploy to e2e.** `pnpm --filter "./packages/*" run build`; deploy `dev` to
   the e2e Trigger.dev project and the e2e app; wait for `/api/health` 200.
6. **Verify.** Run the phase test plan: local gates, the live suite on e2e
   (two consecutive green runs), security tests, AI evals where listed, the
   rollback rehearsal. Collect evidence.
7. **Fix loop.** Each failure becomes a ClickUp fix task naming the failing
   test ID; back to step 4. Same failure after 3 fix attempts → §2.3.
8. **Goal check.** Walk the phase goal as a user would (scenario in the phase
   section) on the e2e app and confirm the outcome, not just green tests.
9. **Complete.** Write `docs/evidence/phase-N.md`; add the §11 line
   `YYYY-MM-DD — Phase N complete (agent, plan §2.2); release pending Seun`;
   mark §6; open the release PR; notify Seun; start the next phase on `dev`.
10. **Release (async, when Seun merges).** Deploy `main` to staging and the
    main Trigger.dev project's `prod`, run the release smoke (§7 item 7),
    record `YYYY-MM-DD — Phase N released` in §11.

### 2.3 Stop and escalate (the loop halts and tells Seun why)

- The same failure survives 3 fix attempts (state what was tried and why it failed)
- A security test finds a real leak or bypass in code already on `main`
  → contain first (§2.1 item 4), then report
- Spend reaches 80 % of a cap (D5, C12), or TypeSafe returns quota errors
- A DoD target cannot be met without changing scope, a decision or the stack
- A new pending decision appears (never pick an option alone)
- ServiceNow `dev420188` hibernates for more than 2 h (needs a human wake-up)
- The Dokploy host has < 1 GB free memory (stop the e2e app first)
- Seun replies `stop`

### 2.5 Internal API (built in P3-T1; both apps; token `INTERNAL_API_TOKEN`)

All endpoints compare the bearer token in constant time, return 401 on any
mismatch, record a security event, and never return raw ticket text,
requester name or email. Security events are aggregated: one row per
(source, kind, minute) with a `count`, so a flood of bad requests cannot
grow the shared DB without bound.

| Endpoint | Purpose | Where |
|---|---|---|
| `GET /api/health/config` | Feature readiness booleans + app version; no values | both (no token) |
| `GET /api/internal/tickets/:id` | Status, `is_test`, triage summary, events (type + time), reviews, notifications, auto-fix rows | both |
| `GET /api/internal/usage?month=YYYY-MM` | LLM USD and TypeSafe call counts month-to-date | both |
| `GET /api/internal/security-events?since=` | Security event list (kind, source, time) | both |
| `POST /api/internal/test-tickets` | Create a ticket through the same intake code (no Turnstile, no IP rate limit), `is_test = true`, key `test:<id>`, optional `testOverrides` | e2e only (404 when `E2E_MODE` is not `true`) |

### 2.6 Ticket status model (enforced by a check constraint and a pure transition function, P3-T2)

`new` → `redacted` → `triaged` → one of:
- `auto` → `helpdesk_pending` → `incident_created` | `incident_skipped_shadow`
- `review_pending` → `approved` (→ `helpdesk_pending` …) | `rejected` | `escalated_manual`

Any state → `failed` (with a `*_failed` event). Illegal transitions throw.
Auto-fix state lives in `autofix_actions` (phase 6), not in `tickets.status`.

## 3. Universal Definition of Done (applies to every phase)

A phase is complete only when ALL of these hold:

1. Every phase task is `done` in ClickUp, merged to `dev` via PR with green CI
   and the required reviews (two for `high-risk`); no task report has an open
   "untested" item.
2. PROJECT §9 gates green on the final `dev` commit: lint, format, types,
   tests + coverage (≥ 80 % overall; ≥ 90 % statements on guard modules:
   redaction, policy, Slack signature, auto-fix precheck, auth, internal-API
   auth, idempotency), build, audit (no critical), gitleaks, integration, e2e.
3. Mutation score (Stryker) ≥ 80 % on the guard modules touched in the phase
   (≥ 90 % for the auto-fix precheck).
4. Semgrep (OSS rules `p/typescript`, `p/nextjs`, `p/secrets`,
   `p/owasp-top-ten`): no unaccepted high finding.
5. Every new migration has up and down files, tested up → down → up on
   Postgres 17.6 with phase-2-shaped rows present; Seun applied the up file;
   `/api/health/config` confirms the new objects.
6. `dev` HEAD is deployed to the e2e app and the e2e Trigger.dev project;
   `/api/health` 200; `.env.example` lists every new variable name.
7. The phase live suite passes on the e2e app twice in a row. A flaky test is
   a bug: it gets a fix task, never a silent retry.
8. Rollback rehearsed on the e2e app: previous deployment restored, health
   checked, rolled forward.
9. No PII canary (§4.3) in any external sink the phase touches (AI calls,
   Langfuse, Slack, ServiceNow, Sentry, email, logs).
10. Goal check passed and recorded.
11. `docs/evidence/phase-N.md` lists PRs, CI runs, test counts, live-suite run
    IDs, Trigger.dev run IDs, metrics, spend, accepted gaps.
12. PROJECT §6/§11 updated, new dependencies logged in §11 (one line each),
    release PR `dev` → `main` open with the `high-risk` task list.

### 4.3 PII canaries

Each live run uses run-unique variants so a hit can be traced to its run:
SSN `078-05-1120`, card `4111 1111 1111 1111`, email `canary+<run>@example.com`,
phone `+61 412 345 678`, IPv4 `203.0.113.42`, IPv6 `2001:db8::42`, API key
`sk-test-CANARY<run>`, AWS key `AKIAIOSFODNN7EXAMPLE`, GitHub token
`ghp_CANARY<run padded to 36>`, password line `Password: Hunter2!Canary<run>`.
`.gitleaks.toml` allow-lists the canary fixture path only (§9).

outbound-HTTP recorder in integration tests (every body sent to TypeSafe, Zen,
Langfuse, Slack, ServiceNow, Resend, Sentry), the Langfuse public API, Slack
`conversations.history` on `#itsupport-e2e`, the ServiceNow Table API, the
Resend email content, and Dokploy + Trigger.dev logs.

### 4.4 Secrets in tests

Live tests get keys only through the approved key-store loader into the test
process environment, and never print them. Test processes get only:
`INTERNAL_API_TOKEN`, the Cloudflare Access service token, the e2e test
signing secret, the e2e Slack bot token (read history), the ServiceNow
integration password (phase 6 setup), the Langfuse and Sentry read keys. They
never get the service-role key or the real Slack signing secret.

There is one Slack app, so the bot token used by tests can also post to the
live demo channel. The test Slack helper therefore accepts only the
`#itsupport-e2e` channel ID and refuses any other (T4.S.06).

## 6. Phases

### 6.1 Phase 3 — AI triage + KB

**Goal.** Every new ticket gets an automatic, typed triage from redacted text
only: one of the 6 `dev420188` categories, priority P1–P4, urgency, a route
(`auto` or `review`), matching KB articles and drafted fix steps. Every AI call
is traced in Langfuse and metered against the caps, and the eval targets in
PROJECT §2 are met on the real pipeline.

**Out of scope.** Posting to Slack (phase 4); writing to ServiceNow (phase 5).
In phase 3 the route is recorded and the status stops at `triaged`.

**Migration 0003 (HIGH-RISK).**
- `tickets`: add `is_test boolean not null default false`; status check
  constraint (§2.6, includes `new` for existing rows).
- `triage_results`: add NULLABLE category, subcategory, priority, urgency,
  route, probabilities jsonb, kb_article_ids uuid[], suggested_fix jsonb,
  model_versions jsonb, triaged_at (phase-2 rows stay valid).
- `kb_articles` (slug unique, title, content, category, assignment_group,
  generated `search tsvector` + GIN index).
- `ai_calls` (id, ticket_id nullable, provider `typesafe|zen`, kind,
  tokens_in, tokens_out, cost_usd nullable, environment, at).
- `security_events` (id, source, kind, window_start, count, sample jsonb
  without PII; unique (source, kind, window_start)) — no FK, so events without
  a valid ticket can be stored; writes are upserts that increment `count`.
- Function `itsupport.ai_budget_reserve(provider, est_cost, est_calls)`: takes
  a transaction advisory lock, sums month-to-date usage, inserts a reservation
  row and returns false when the cap would be exceeded.

### 6.6 Phase 8 — Email intake

**Goal.** An email to the intake address creates a ticket that goes through
the same pipeline as the form (redact, triage, review, incident, reply), with
signature-verified webhooks, no duplicates, no mail loops and no auto-fix.

**Migration.** None expected: idempotency uses `email:<Message-ID>` (C14) and
ignored mail is logged in `security_events`. If a table is needed, it is `0008`
with a down file and a human apply step.

**Tasks.**

| ID | Task | Risk | Depends on |
|---|---|---|---|
